# README Evaluation

This repository provides an experimental framework for evaluating the quality of README files generated by different documentation tools:

* `OSA`
* `LArch`
* `ReadMeReady`
* `OpenCode`

The main entry point is `README_benchmark/README_benchmark.ipynb`. The notebook prepares the dataset, clones the target repositories, stores the original README files and repository structures, executes the selected tools, and evaluates the generated README files using **DeepEval GEval**.

## Project Structure

```text
README_benchmark/
  benchmark_README/
    data/repo_list.csv
    results/
    src/
    README_benchmark.ipynb
    requirements.txt
  OSA/
  larch_eval/
  ReadMeReady_eval/
  .github/
  README.md
```

The `README_benchmark` directory contains only the experiment orchestration code. Each evaluated tool resides in its own directory and uses a separate virtual environment to avoid dependency conflicts.

## Installation

The project is currently configured and tested for **Windows + PowerShell**. Paths and virtual environments assume a Windows environment.

### 1. Clone the Repository

```powershell
git clone https://github.com/fl1pcoin/README_benchmark
```

### 2. Create the Root Environment

From the project root:

```powershell
cd README_benchmark
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r .\benchmark_README\requirements.txt
python -m ipykernel install --user --name vkr-readme-eval --display-name "README_benchmark"
```

In Jupyter Notebook or your IDE, select the **README_benchmark** kernel.

### 3. Create Tool Environments

Each tool should have its own virtual environment:

```text
OSA/.venv/
larch_eval/.venv/
ReadMeReady_eval/.venv/
```

If these environments already exist, they do not need to be recreated.

To create them from scratch:

```powershell
cd README_benchmark\OSA
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
pip install -e .
deactivate

cd README_benchmark\larch_eval
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
pip install -e .
deactivate

cd README_benchmark\ReadMeReady_eval
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
pip install -e .
deactivate
```

### 4. Install OpenCode

`OpenCode` is used as an external CLI tool and does not require a dedicated directory or virtual environment inside the repository. It must be installed globally so that it is available from both PowerShell and the Jupyter kernel.

First, verify that Node.js is installed:

```powershell
node --version
npm --version
```

If Node.js is not installed, install the latest LTS version from the official Node.js website and restart PowerShell.

Install OpenCode:

```powershell
npm install -g opencode-ai
```

Verify the installation:

```powershell
opencode --version
```

During benchmark execution, OpenCode is launched through OpenRouter. For each evaluated model, the runner automatically creates a temporary `opencode.config.json` in:

```text
benchmark_README/results/<run_name>/tools/opencode/<model_label>/opencode.config.json
```

The model identifiers defined in the notebook configuration are automatically converted to the OpenCode/OpenRouter format:

```text
openai/gpt-4.1                 -> openrouter/openai/gpt-4.1
anthropic/claude-sonnet-4      -> openrouter/anthropic/claude-sonnet-4
google/gemma-3-27b-it          -> openrouter/google/gemma-3-27b-it
```

## API Keys

Create a `.env` file in:

```text
benchmark_README/.env
```

with the following variables:

```env
OPENROUTER_API_KEY=...
OPENAI_API_KEY=...
OPENAI_API_BASE=https://openrouter.ai/api/v1
OPENAI_BASE_URL=https://openrouter.ai/api/v1
GIT_TOKEN=...
GITHUB_TOKEN=...
HF_TOKEN=...
```

Variable descriptions:

* `OPENROUTER_API_KEY` is required to access models through OpenRouter.
* `OPENAI_API_KEY` may contain the same value as `OPENROUTER_API_KEY`, since some tools expect this variable name.
* `OPENAI_API_BASE` and `OPENAI_BASE_URL` redirect OpenAI-compatible clients to OpenRouter.
* `GIT_TOKEN` or `GITHUB_TOKEN` is used for GitHub API authentication and helps avoid rate limits.
* `HF_TOKEN` is required by the Hugging Face dependencies used by ReadMeReady and LArch.

## Dataset

The list of repositories is stored in:

```text
benchmark_README/data/repo_list.csv
```

Expected columns:

* `repo_url`
* `repo_name`
* `commit_sha`
* `commit_date`

For each repository, the benchmark:

* clones the repository,
* checks out the specified commit,
* saves the original README,
* exports the repository structure as JSON.

## Running the Benchmark

Open:

```text
benchmark_README/README_benchmark.ipynb
```

The first notebook cell contains the experiment configuration:

```python
EXPERIMENT = {
    "run_name": "default_run",
    "data_csv": "data/repo_list.csv",
    "tools": {
        "osa": {"enabled": True},
        "readmeready": {"enabled": True},
        "larch": {"enabled": True, "mode": "local"},
        "opencode": {"enabled": True},
    },
    "models": [
        "openai/gpt-4.1",
        "anthropic/claude-sonnet-4",
        "google/gemma-3-27b-it",
    ],
    "judge": {
        "api": "openrouter",
        "base_url": "https://openrouter.ai/api/v1",
        "model": "gpt-4.1",
    },
    "reset": {
        "repos": False,
        "tool_outputs": False,
        "evaluation": False,
    },
    "limit_repos": None,
}
```

To evaluate the full dataset, leave:

```python
"limit_repos": None
```

For a quick test run:

```python
"limit_repos": 1
```

To regenerate tool outputs while keeping cloned repositories and previous evaluations:

```python
"reset": {
    "repos": False,
    "tool_outputs": True,
    "evaluation": False,
}
```

After configuring the experiment, execute all notebook cells.

## README Evaluation

README quality is evaluated using **DeepEval GEval**.

`ACTUAL_OUTPUT` is passed as JSON:

```json
{
  "readme": "generated README",
  "repo_structure": "repository structure in JSON format"
}
```

`EXPECTED_OUTPUT` is the original repository README.

GEval evaluates whether the generated README:

1. Matches the repository structure.
2. Clearly describes the project's purpose.
3. Includes installation and setup instructions.
4. Provides meaningful usage examples.
5. Documents dependencies or system requirements.
6. Is well-structured, readable, and easy to understand.

Evaluation results are saved to:

```text
benchmark_README/results/<run_name>/evaluation/eval_rows.csv
benchmark_README/results/<run_name>/evaluation/final_summary.csv
```

## Tool-Specific Notes

### OSA

The runner launches OSA using:

```text
OSA/.venv/Scripts/python.exe -m OSA.osa_tool.run_multi_process
```

The runner also configures `PYTHONPATH` to include both the project root and `OSA/osa_tool`, since the current implementation mixes imports such as `OSA.osa_tool...` and `config.settings`.

### LArch

LArch is executed locally through its internal Python API without using an external endpoint.

On Windows, the benchmark uses the `file_names` context creator because the default `entrypoint` context creator relies on `signal.SIGALRM`, which is unavailable on Windows.

### ReadMeReady

ReadMeReady runs in batch mode, where a single subprocess processes all selected repositories for a given model. This allows Hugging Face embeddings to be loaded into memory only once per model execution instead of once per repository.

On Windows, the runner also works around two practical issues:

* the absence of the native `libmagic` library;
* the `prompt_toolkit.clear()` error that occurs when subprocesses are executed without a Windows console buffer.
